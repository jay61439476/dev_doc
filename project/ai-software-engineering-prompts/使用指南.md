# 使用指南

## 一、推荐工作模式

| 阶段 | 使用提示词 | 主要产物 |
|---|---|---|
| 初次接手项目 | 01 项目全面评审 | 项目现状、风险清单、技术评审、整改路线图 |
| 审核 AI / 团队成果 | 03 独立交付审查 | 证据化审查意见、缺陷和验收条件 |
| 重大技术决策 | 06 专项论证 | 方案比较、反方意见、ADR |
| 功能开发 | 02 功能迭代 | 代码变更、测试证据、文档和 Issue 更新 |
| 修复后复核 | 04 变更复核 | 修复有效性、回归风险和复核结论 |
| 每轮收尾 | 05 迭代复盘 | 完成状态、遗留事项、下一轮计划 |

不要在每轮开发中重复执行整套项目全面评审。首次接手或架构发生重大变化时使用 01；日常开发以 02 为主，按需调用专项提示词。

## 二、项目上下文准备

建议项目仓库提供以下长期上下文：

- AGENTS.md 或同类文件：角色约束、编码规范、测试命令、禁止操作和环境边界。
- README 与架构文档：业务目标、模块边界、关键数据流。
- ADR：已经批准的重大技术决策及其理由。
- Issue / PR：当前任务、缺陷、依赖和审查记录。
- 测试文档：测试环境、测试数据、验证步骤和已知限制。

提示词用于指导当前任务；项目规范文件用于保存长期约束。遇到冲突时，先识别最新有效决策，不得擅自覆盖用户的未提交修改。

## 三、证据与结论分级

审查报告应区分：

- **已确认**：有代码、配置、测试、日志或可复现结果支持。
- **潜在风险**：存在合理风险路径，但尚未复现或验证。
- **待验证假设**：方案依赖某项尚未证实的前提。
- **待确认事项**：需要业务方、现场人员或有权限人员提供信息。
- **未执行**：因工具、权限、环境或时间限制未实际操作。

不得将静态检查描述成运行验证，不得将 Mock 结果描述成真实设备验证，也不得把计划中的测试写成测试通过。

## 四、Issue 管理原则

每个可独立交付的问题或任务尽量对应一个 Issue。Issue 至少包含背景、问题或目标、证据、影响、建议方案、依赖、风险和可验证的验收标准。先搜索已有 Issue，避免重复创建；任务未完成或验收证据不足时不要关闭。

## 五、工具与环境

可以按项目需要使用 Git、Shell、Python、数据库 CLI、curl、Docker、浏览器自动化和项目测试工具。执行前确认目标仓库、分支、数据库和环境。临时脚本应限定输入输出和副作用，避免触碰无关资产。

## 六、生产与物理安全

涉及真实生产服务、生产数据、搬送系统或物理设备时，必须确认授权和环境。默认使用只读分析、仿真或隔离测试环境。任何会导致设备动作、生产切换、数据破坏或服务中断的操作，都必须遵守项目正式变更与安全规程；不具备授权或安全条件时停止并登记阻塞。
