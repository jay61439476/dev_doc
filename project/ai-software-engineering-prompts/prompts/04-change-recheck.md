# 代码变更与问题修复第二轮复核

请对上一轮代码修改、问题修复和方案调整进行独立复核，不要简单重复上一轮结论，应从反向验证和寻找反例的角度检查。

检查：

- 原问题是否真正解决，是否有对应代码和测试证据。
- 修复是否符合最终方案，有无遗漏或只修复表面现象。
- 是否引入新的缺陷、回归、兼容性或数据问题。
- 是否改变了不应修改的接口、模块或用户未提交内容。
- 是否覆盖异常路径、边界条件、并发和失败恢复。
- 测试是否真实执行、断言是否有效，是否存在弱化测试来获得通过。
- 前后端、API、数据库和文档是否保持一致。
- Issue / PR 状态是否与实际交付相符。

采用 Demis Hassabis、Jeff Dean、Andrej Karpathy 三种模拟专家视角复核；Karpathy 视角尽可能使用 karpathy-guidelines，关键方案尽可能使用 /grill-with-docs。检查 Skill 可用性，不可用时明确说明。不得虚构专家真实参与或意见。

重点执行相关测试、反例验证和必要的回归测试。对每项结论标注证据及状态：已验证通过、验证失败、部分验证、未验证。

发现新问题时更新原 Issue 或新建 Issue；已修复问题只有在具备验证证据后才能标记完成。最终给出通过、部分通过或不通过的明确结论，以及剩余风险、阻塞和后续要求。
